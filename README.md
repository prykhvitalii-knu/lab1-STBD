# Система управління великим магазином (Store Manager)

Цей проєкт є реалізацією бази даних та бекенд-шару для системи управління великим магазином. Проєкт демонструє використання розширених можливостей реляційних баз даних (PostgreSQL) та взаємодію з ними з коду на C# з використанням патернів Repository та Unit of Work.

## Виконання вимог завдання

Проєкт повністю відповідає поставленому технічному завданню:

1. **Схема БД:** Розроблено схему бази даних (DBML файл додається), що містить **15 сутностей** із налаштованими зв'язками `1:M` та `1:1`.
2. **Аудит та Soft Delete:** 
   * Сутності `Product`, `Customer`, `Employee` тощо підтримують "м'яке видалення" (Soft Delete) за допомогою поля `IsDeleted` та фіксують дату видалення.
   * Реалізовано поля `UpdatedAt` та `UpdatedBy` для фіксації останніх змін.
3. **Реалізація СУБД:** Використано **PostgreSQL**.
4. **Об'єкти БД (Програмування БД):** Створено понад 10 об'єктів бази даних:
   * **Triggers & Functions:** Автоматичне оновлення поля `UpdatedAt` при зміні даних.
   * **Views:** `vw_ActiveProducts`, `vw_ActiveEmployees`, `vw_InventoryStatus` для зручної та безпечної вибірки не видалених записів.
   * **Stored Procedures:** `sp_SoftDeleteProduct`, `sp_AddOrderItem`, `sp_UpdateEmployee` для інкапсуляції бізнес-логіки в БД.
5. **Індекси:** Створено два типи індексів:
   * Стандартні B-Tree індекси для первинних/зовнішніх ключів та полів пошуку.
   * Partial (Filtered) індекси (наприклад, `WHERE IsDeleted = FALSE`) для оптимізації вибірок при Soft Delete.
6. **Робота з коду:** Написано консольний додаток на C# (.NET) з використанням мікро-ORM Dapper. Реалізовано патерни **Repository** та **Unit of Work**. Доступ до даних (вибірка та зміна) здійснюється **виключно через Views та Stored Procedures**.

---

## Структура проєкту

* `docker-compose.yaml` — конфігурація для швидкого підняття сервера PostgreSQL локально.
* `scripts/` — папка з SQL-скриптами для ініціалізації БД (створення таблиць, індексів, процедур, тригерів та тестових даних).
* `StoreManagerApp/` — C# консольний додаток, який містить логіку Unit of Work та виконує демонстраційні сценарії.

## Інструкція з запуску

### Крок 1: Запуск бази даних
Для запуску вам знадобиться встановлений [Docker Desktop](https://www.docker.com/products/docker-desktop).
Відкрийте термінал у кореневій папці проєкту та виконайте:
```bash
docker-compose up -d
```
*Ця команда запустить контейнер із PostgreSQL на порту `5432` з базою `StoreDB`.*

### Крок 2: Ініціалізація бази даних
Увійдіть в інтерактивну консоль PostgreSQL у контейнері:
```bash
docker exec -it store_postgres psql -U store_admin -d StoreDB
```
По черзі вставте та виконайте у консолі SQL-скрипти з папки `scripts`:
1. Скрипт створення таблиць та індексів (`init.sql`).
2. Скрипт створення Functions, Triggers, Views та Procedures (`programmability.sql`).
3. Скрипт наповнення бази тестовими даними (`seed.sql`).

Для виходу з консолі введіть `\q` та натисніть Enter.

### Крок 3: Запуск C# додатку (Демонстрація)
Переконайтеся, що у вас встановлено [.NET SDK](https://dotnet.microsoft.com/download). 
Перейдіть у папку додатка та запустіть його:
```bash
cd StoreManagerApp
dotnet run
```

### Що покаже програма при запуску?
Додаток автоматично виконає три сценарії, що доводять працездатність системи:
1. Виведе список товарів, **використовуючи виключно View** `vw_ActiveProducts`.
2. Створить нове замовлення, використовуючи **Unit of Work**. Викличе **збережену процедуру** `sp_AddOrderItem`, яка спише залишки на складі.
3. Продемонструє роботу **Soft Delete**, викликавши процедуру `sp_SoftDeleteProduct`, після чого доведе, що товар зник із View, але залишився в базі даних.

## Лабораторна робота 2: SQL vs NoSQL (Доповнення)

У рамках другої лабораторної роботи предметну область було розширено для тестування та порівняння реляційної (PostgreSQL) та нереляційних (MongoDB, Redis) баз даних.

### Виконання вимог:
1. **Обґрунтування та розширення вимог:** В інтернет-магазинах товари мають динамічні характеристики (колір, процесор, вага) та відгуки. В SQL це вимагає створення структури EAV (Entity-Attribute-Value) та використання складних і повільних `JOIN`. Тому ці дані доцільніше винести в **Document-oriented NoSQL (MongoDB)**, де товар, його характеристики та відгуки зберігаються як єдиний агрегований JSON-документ, що зчитується за одне звернення до диска.

2. **Генерація даних:** Написано C# скрипт (з використанням бібліотеки Bogus), який генерує **1000 реалістичних товарів** (разом із 3000 відгуків та 2000 характеристик).

3. **Реалізація в SQL:** Дані записуються у PostgreSQL з розбиттям на 4 нормалізовані таблиці (`Product`, `ProductReview`, `ProductAttribute`, `ProductAttributeValue`).

4. **Реалізація в NoSQL:** Ті ж самі дані записуються в колекцію MongoDB як цілісні об'єкти.

5. **Тестування швидкодії (Benchmark):** Програма імітує 500 запитів "відкриття сторінки товару", виконуючи 3 SQL-запити з `JOIN` для PostgreSQL та 1 простий запит документа для MongoDB, після чого порівнює час виконання у мілісекундах.

6. **Інша NoSQL база:** Додано **Redis (Key-Value)** для розв'язання нішевої задачі — зберігання "Кошика покупця", який має швидко читатись, часто оновлюватись і автоматично видалятись (через TTL - Time To Live).
